## 这是什么

一个针对 `core/` 的**防漏文件**校验工具，外加三处文档修正。

起因是 v1.1.0 修的那个阻断级缺陷（`.gitignore` 的 `models/` 误伤
`core/retrochimera/models/`）。那个 bug 的恶劣之处在于**没有任何机制能发现它**：

- 本机一切正常 —— `retrochimera` 是 `pip install -e .` 装的，缺的文件
  被本机副本悄悄补上了
- 同步上游用的 `robocopy` 也发现不了 —— 它只覆盖**已有**文件，
  新版本新增的源码若被 ignore 误伤，就是「复制成功但没进 git」

所以这次把当时的手工审计固化成了一条命令。

## ✨ 新增 `scripts/verify_vendored.py`

拉取上游 `v1.3.0` 的文件树与 blob SHA，与本仓逐个比对，报三类问题：

| 类别 | 含义 |
|---|---|
| `[缺失]` | 上游有、本仓没有 |
| `[未跟踪]` | 本地存在，但没进 git ← 那个 bug 的典型表现 |
| `[不一致]` | 内容与上游不同 |

自动排除两类**有意差异**：

- `EXPECTED_DIFF` —— 登记在 `core/VENDORED.md` 的本地化改动（目前只有
  `pyproject.toml` 的静态版本号）
- `EXPECTED_ABSENT` —— 上游的 CI 配置。⚠️ 其中 `release.yml` **千万不能搬**：
  它会往 **PyPI 发布并打 tag**，搬过来会误发布、误打标签

### 用法

```bash
python scripts/verify_vendored.py                 # 校验 v1.3.0（默认）
python scripts/verify_vendored.py --ref v1.3.1    # 校验别的版本
python scripts/verify_vendored.py --ref main      # 校验上游主分支
python scripts/verify_vendored.py --list-tags     # 先看有哪些可用版本
```

退出码 `0` = 全部一致，`1` = 有问题（适合放进 CI）。

### 可靠吗

脚本做了**反向测试** —— 不验证「能不能检出问题」的校验工具等于摆设：

- 正常态 → 通过
- `git rm --cached` 制造「未跟踪」→ ✅ 准确报出
- 移走文件制造「缺失」→ ✅ 准确报出

## 📝 文档修正

**1. `core/VENDORED.md`：原文说与上游「逐字节一致」—— 这已不准确。**

`.gitattributes` 声明了 `*.md text eol=lf`，换行符被规范化过，
`SUPPORT.md` 等文件已经不与上游逐字节相同（内容一致，仅换行符不同）。
表述改为「内容一致」，并说明如何自检。

**2. `core/VENDORED.md`：「更新上游版本」章节原先完全没有校验环节。**

覆盖完就完事，没有任何步骤能发现漏文件。这正是问题能溜过去的原因，
现已补上三步自检（含一条白名单式的 `git status --ignored` 检查）。

**3. README 中英文「已知坑」各补一条**：`.gitignore` 的目录锚定规则
及其隐蔽性（`/models/` vs `models/`）。

## 🔍 顺便做的完整性审计结论

既然有了比对工具，就把 `core/` 整体查了一遍 —— **内容完整，无其他缺失**：

- **121 个文件 blob SHA 与上游 v1.3.0 完全一致**
- 2 个差异均属已登记的有意改动（`pyproject.toml`、`SUPPORT.md`）
- 4 个是刻意不搬的上游 CI 配置

顺带确认一件容易被误解的事：**`core/retrochimera/__pycache__/` 在 GitHub 上
没有是正确的**。它是 Python 字节码缓存，文件名带 `cpython-39` 这类
magic tag，换 Python 版本即失效，跨机器毫无意义 —— 与被误伤的
`core/retrochimera/models/`（源码）性质正好相反。
