# v1.2.0 —— 物质查询双数据源（PubChem / ChemIndex）

新增 `POST /api/substance`：**一个接口、两个可选数据源**，覆盖「CAS 号 / 物质名称 → 结构 + 物性」。
同时补上 CI 会暴露的两处问题，并让 `desktop/` 下的发布/运维脚本入库。

---

## ✨ 新接口：`POST /api/substance`

请求体：

```json
{"terms": "50-78-2", "source": "pubchem", "choice": "cas"}
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `terms` | 任意 | CAS 号（`50-78-2`）或物质名称（`aspirin`） |
| `source` | `pubchem`（默认）/ `chemindex` | 用哪个库 |
| `choice` | `cas` / `name`，可省略 | 省略时后端按形态自动判断 |

成功返回 `smiles` + `name` + `formula` + `mw` 等；**查无此物不是错误**，
返回 `{ok:false, found:false}` 配 HTTP 200 —— 前端要能区分「查不到」和「接口坏了」。

### 两个源各擅长什么

| | PubChem | ChemIndex |
|---|---|---|
| CAS → 结构 | ✅ | ✅ |
| 名称 → CAS | ✅（中文名也行） | ✅（仅英文名） |
| 熔点 / 沸点 / 闪点 / 溶解度 / 蒸气压 | 部分 | ✅ 齐全 |
| 危害符号 / 风险代码 / 安全说明 | ✅ | ✅ |
| InChI | — | ✅ |
| 供应商列表 | — | ✅（见原站） |

⇒ **互补而非重叠**。PubChem 覆盖最广（中文名可查），ChemIndex 的物性与危害档案更全。
前端把它们做成一个下拉，选择存 localStorage，换一次长期生效。

## 🔴 为什么 Chemistry 查询必须走后端（前端直连不可行）

接入前实测了 ChemIndex，撞上两道**前端过不去**的坎：

1. **没有 CORS 头** —— 响应头里没有 `Access-Control-Allow-Origin`，
   浏览器 `fetch` 直接被 CORS 策略拒掉。
2. **JS 反爬挑战** —— 首次请求返回约 660 字节的「正在进行安全检查」页，
   其中一段 JS 把响应里的 `_0x2` 写进 `HW_CHECK` cookie 再 `location.reload()`。
   挑战值是**响应体自带的**，所以服务端用正则抽出来当 cookie 重发即可通过
   （纯 HTTP 客户端若不会这一步，第一发必吃这个页面）。
   另外不带浏览器 UA 会被直接 433 拒掉。

⇒ 只能服务端代理。PubChem 本来有 CORS、前端能直连，但为了让两个源**共用一个入口**，
也一并走了后端 —— 否则前端要维护两套分支逻辑（一套本地、一套走代理）。
代价是一次本机 HTTP 往返（毫秒级）。

### InChI → SMILES 在后端转

ChemIndex **不给 SMILES**，只给 InChI。前端用的是 **RDKit MinimalLib**，
它只有 `get_inchi`（结构 → InChI）、**没有反向** ⇒ 前端做不了这个转换，
必须在后端用完整版 RDKit 转。

🔴 **转换后必须中性化**。ChemIndex 的 InChI 常带 `/p-1`（去质子层），
直接转会得到阴离子。实测阿司匹林 `50-78-2`：

```
原样转   CC(=O)Oc1ccccc1C(=O)[O-]    ← 阴离子
中性化后 CC(=O)Oc1ccccc1C(=O)O       ← 与 PubChem 一致
```

不中性化的话，同一种物质从两个源查出来会长得不一样。

## 🛠 可靠性：强制直连

两个查询模块都显式 `ProxyHandler({})` 绕开环境里的 `HTTP_PROXY` / `HTTPS_PROXY`。

原因（实测踩到）：机器上遗留的代理变量指向一个**已失效**的本地端口时，
所有外网请求报 `os error 10061 目标计算机积极拒绝` ⇒ 表现为「上游查询 502」，
而报错完全不像是代理问题，极易查错方向。物质查询这种直接打公网的请求，
显式直连最稳。已**带着失效代理重启服务实测通过**。
